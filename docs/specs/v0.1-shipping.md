## Problem Statement

The thing works, but nobody who is not already inside this working directory can use it.

Concretely, from the point of view of someone who saw a link to this repo:

1. **There is nothing to install.** The README's install block advertises a `curl | sh` URL that does
   not exist and a `raw.githubusercontent.com/0DukePan/handmedown/main/install.ps1` that is not in the
   repository. `pkg install hand` is not a real Termux package. A visitor who follows the README gets a
   404 at the first command, which is worse than no README.
2. **There is nothing to download.** No tag has been cut, so the release workflow has never run. There
   are no archives, no `SHA256SUMS.txt`, and no version string on any binary.
3. **There is no picture.** The value proposition is "kill the control plane and nothing breaks", which
   is a claim about a terminal, and a claim about a terminal needs a 15-second GIF. Without one, the
   README asks the reader to imagine the demo. Nobody imagines the demo.
4. **The claims are unverified from the outside.** `docs/WHY-TWO-LANGUAGES.md` cites a binary size and a
   release size. `CHANGELOG.md` cites the same numbers. Nothing regenerates or checks them, so the only
   thing keeping them true is somebody remembering to re-measure. They have already been wrong once (a
   pre-websocket 2.40 MB measurement outlived the build that produced it).

The common thread: **everything that exists is source-shaped, and shipping is artefact-shaped.** The
repository is a good source tree pretending to be a product.

## Solution

Cut a verified `v0.1.0` release and make the README's first command work on Windows, macOS, Linux and
Termux.

From the user's perspective:

1. `hand --version` reports something like `hand v0.1.0 (windows/amd64)` instead of `hand dev`.
2. The Windows installer downloads the right archive for their machine, verifies it against the
   published checksum, refuses to install on a mismatch, and puts the binary somewhere on the user
   `PATH` without administrator rights.
3. Every release carries `hand_<os>_<arch>` binaries for six targets plus a `SHA256SUMS.txt`.
4. The README's hero is a GIF that runs the real demo, and the GIF is generated by a script in the
   repository rather than recorded once by hand.
5. The numbers quoted in the docs are produced by a command, and a test fails when they drift.
6. `hand demo` shows the crash-and-recover story on a single machine with no devices involved, so the
   first thing a cautious user runs does not require trusting anybody else's hardware.

## User Stories

### Installing

1. As a new user on Windows, I want a one-line install command that works, so that I do not have to
   install Go, Rust or an Erlang toolchain to try a task runner.
2. As a new user on Windows, I want the installer to put `hand` on my `PATH` without admin rights, so
   that it does not need a corporate laptop's permission prompt.
3. As a new user on Windows, I want the installer to tell me to open a new terminal, so that I am not
   confused by `hand` being missing immediately after a successful install.
4. As a new user on macOS, I want a `curl | sh` install that fetches the right `darwin/arm64` binary, so
   that it works on an Apple Silicon machine without Rosetta.
5. As a new user on an Intel Mac, I want the installer to pick `darwin/amd64`, so that it works on older
   hardware too.
6. As a new user on Linux, I want the installer to pick `amd64` or `arm64` by detecting my
   architecture, so that I do not have to know which one I have.
7. As a user installing into Termux on an Android phone, I want the `linux/arm64` build documented as
   the Termux path, so that I know a phone is genuinely supported and not a bullet point.
8. As a cautious user, I want the installer to verify a SHA256 checksum before installing anything, so
   that a truncated or tampered download fails loudly instead of installing something broken.
9. As a cautious user, I want the installer to refuse to continue when the download is corrupt, so that
   the failure is a clear error rather than a mysterious crash later.
10. As a cautious user, I want to be able to install a specific version, so that I can pin a version in
    my own scripts.
11. As a cautious user, I want an `--uninstall` behaviour or documented manual removal, so that
    installing is reversible.
12. As a user behind a proxy or on a slow connection, I want the installer to fail with a readable
    message when it cannot reach the release, so that I do not debug a network problem as a broken tool.
13. As a user installing twice, I want the second install to be idempotent, so that re-running is safe.
14. As a user of both a laptop and a desktop, I want the same installer to work on both, so that I do
    not learn two procedures.

24. As a user of a versioned install, I want the archives to be predictably named, so that a script can

## Implementation Decisions

### Distribution model

- **A release is a tagged `v*` push.** The tag is the only input. Everything else is derived, so the
  binary version, the archive names and the release title cannot disagree.
- **Asset naming is a contract**, not an implementation detail: `hand_<goos>_<goarch>[.exe]` for the
  agent, `handmedown-brain_<version>_<os>_<arch>.tar.gz` for the brain, plus `SHA256SUMS.txt`. Installers
  construct URLs from this; changing it is a breaking change to the install surface.
- **Termux uses the `linux/arm64` artefact**, documented explicitly. `GOOS=android` would require cgo and
  an NDK for no benefit, since Termux is an ordinary Linux userland on an arm64 kernel. This is a
  documentation decision with a packaging consequence, so it is recorded rather than assumed.
- **The brain is packaged for its build platform only.** Cross-OS BEAM releases are not a thing; the
  brain is compiled from source on whatever machine runs it, and the release archive is a convenience for
  the common case.

### Installer

- **One `install.ps1` for Windows**, no administrator rights, installing under the user's local app data
  directory and appending to the user `PATH` idempotently.
- **One `install.sh` for macOS and Linux**, detecting OS and architecture, downloading the matching
  artefact, verifying the checksum, and installing to a user-writable prefix.
- **Verification is mandatory, not optional.** Both installers download `SHA256SUMS.txt` first, find the
  line for their artefact, and refuse to install on mismatch. A `--no-verify` escape hatch is
  deliberately *not* provided: an installer that can skip verification is an installer that will skip
  verification.
- **Version pinning** via an environment variable (for example `HAND_VERSION`) falling back to the latest
  release. Both installers share the same variable name.
- **Idempotent**: installing twice replaces the binary and does not duplicate the `PATH` entry.
- **Readable failure modes**: unreachable release, missing asset in the checksum file, unparseable
  checksum line, and checksum mismatch each produce a distinct message that says what to do.

There is a known Windows/PowerShell trap that this work must not repeat: when a response has no charset,
`Invoke-WebRequest` returns a byte array, so string operations silently see numbers and every parse
fails. The existing `tattletale` installer in this workspace already documents the trap and the fix;
the new installer decodes explicitly and the tests cover it.

### Agent surface for shipping

- `hand version` (already present) gains a real version string injected at link time, keeping its current
  output shape so existing scripts keep parsing it.
- **New `hand demo` command.** It runs the real engine — the same journal, output store and runner as
  `hand run` — over a small generated fixture set in a temporary directory, interrupts itself to
  demonstrate recovery, and reports where it wrote its files. It is a real run, not a canned transcript,
  which is what allows the GIF to be generated from it.
- `hand demo` is excluded from the "mesh" story: it needs no brain and no second device.

### Demo asset generation

- A script generates the terminal recording as a sequence of frames, and a second step assembles the
  GIF. The frames are rendered from text the tool actually produced, captured during a real run, so the
  asset cannot claim behaviour the tool does not have.
- The dashboard screenshot is captured from a running brain with a seeded state, not hand-drawn.
- Both assets are committed, but both are reproducible by command, and both have size budgets.

### Claim verification

- Documented numbers (agent binary size, brain release size) are produced by a script that builds the
  relevant artefacts and writes the measured values into the docs' tables between markers.
- A check fails when the committed values differ from the measured ones, so drift is a test failure
  rather than a stale sentence.
- Every fenced command in the README is checked against the actual CLI surface: the subcommands it names
  must exist, and flags it shows must be accepted. This catches the current 404 class of bug by
  construction.

### Not changed

- No changes to the scheduler, the lease protocol, the journal format or the wire protocol version. This
  work is packaging and documentation; if it starts requiring protocol changes, something has gone wrong.
- No new runtime dependencies in either half.

## Testing Decisions

### What makes a good test here

Test what a user or a maintainer can observe, not how it is implemented:

- **Observable:** the installer exits non-zero on a bad checksum and leaves nothing on `PATH`; the
  installed binary prints a version containing the tag; `SHA256SUMS.txt` contains a line per committed
  artefact; the README's commands resolve against the CLI; the committed size numbers match the
  measured ones; generated assets stay within their byte budget.
- **Not worth testing:** the internal helper that decides which artifact name to download (covered
  through the installer's behaviour), the frame generator's drawing primitives, markdown formatting, or
  the exact wording of an error message beyond the fact that it names the problem.

Assertions should be behavioural and forgiving of cosmetic change: check that a version string *contains*
the tag and the platform rather than matching one exact spelling; check a budget as an upper bound rather
than an equality.

### Seams (agreed with the user)

Four seams, all at boundaries a user already sees, none of them new:

1. **`install.ps1`** — highest available seam. Driven against a temporary install root and a stubbed
   release (a local directory of fixture artefacts plus a checksum file), so the test exercises the real
   script end to end without touching the network and without modifying the machine's `PATH`.
2. **The release workflow** — a static parse test asserting the artefact matrix, the checksum step and
   the guard that fails the job when an expected artefact is missing. This mirrors the existing
   validation approach already used for the workflow and issue-form YAML in this repo.
3. **`docs/` assets and the demo** — assertions on the generated artefacts: they exist, are non-empty,
   are within their byte budgets, and the commands they depict are present in the CLI surface.
4. **Documented claims** — the doc/marker consistency check described above.

No new test seam is introduced anywhere in the agent or the brain. The scheduler, journal and lease
behaviour are already covered by `scripts/proofs.ps1`, `scripts/e2e.ps1`, the Go tests and the ExUnit
suite, and this work does not touch them.

### Modules exercised

- Existing: the CLI dispatch (for `hand demo` and `hand version`), the job engine (reused by the demo,
  not modified), and the existing proof scripts (unchanged, re-run as the regression gate).
- New: the two installers, the asset-generation script, the claim-verification script, and the release
  workflow.

### Prior art in this repository

- `scripts/proofs.ps1` and `scripts/e2e.ps1` establish the house style for integration tests: spawn real
  processes, kill them for real, assert on observable state afterwards, and keep the work directory for
  inspection when something fails.
- `brain/test/handmedown/schedule_test.exs` shows the preference for state assertions over
  message-absence assertions; the same caution applies to any "the installer did nothing" check.
- The existing lifecycle-YAML validation in this workspace is the prior art for the workflow seam.

## Out of Scope

- **Publishing.** Cutting the tag and running the release is an owner action that requires a remote and
  an authenticated `gh`; this spec prepares everything up to that point.
- **Code signing / notarisation.** Signing certificates and Apple notarisation are a later, commercial
  concern. The README should be honest that binaries are unsigned, and say how to build from source.
- **Homebrew, winget, AUR, Docker images.** One installer per platform family is enough for v0.1; third-
  party package managers are follow-up work once there is a release history to point at.
- **Termux second-tier work** (duty-cycle capping, battery gates on the phone) — that is the M8 stretch,
  a product change rather than packaging.
- **Second-brain clustering / standby adoption.** Same: M8, deliberately cut.
- **TLS on the agent link.** Documented limitation, tracked in the security notes, not fixed here.
- **A landing page or website.** The README is the landing page.
- **A packaged brain for three platforms.** Build-from-source is documented instead.
- **The GIF's content style** (fonts, colours, typography of the recording). The spec fixes the story it
  tells, not the art direction.

### Ordering

The installers depend on the asset names; the asset names depend on the workflow. So the sequence is
workflow naming first, then installers, then asset generation, then claim verification. `hand demo` must
land before the GIF, because the GIF is generated from it.

### Why this is a spec and not a task list

The interesting decisions are all contracts between artefacts: the naming scheme both installers parse,
the checksum format both installers verify, the markers the docs use to bracket measured numbers, and the
single source of truth for a download URL. Those are cheap to state now and expensive to discover after
two script variants exist.
